## Runtime and composition architecture

PHP 8.5.9 · Fat-Free Framework 3.9 · PHP-DI 7 / PSR-11 · PostgreSQL · server-rendered HTML.

- `public_html/index.php` hardcodes the deployed code root `/usr/local/lib/php/catto-learning/current` and calls `App::run($codeRoot, $instanceRoot, $publicRoot)`. Code, instance (`.env`, `themes/`, `storage/`) and public web roots are three distinct trees.
- **All routes live in one place**: `src/Application/App.php`. To map a URL to code, grep there first. Routes are registered through `RouteRegistrar` as native F3 `Class->method` callbacks.
- PHP-DI is registered as F3's native `CONTAINER`, so controllers are constructed lazily by the container when a route matches. Enforced invariants (`tools/check-runtime-hazards.php`): no custom `LazyControllerHandler`, no eager controller construction, no restored `AppContext` / `ServiceFactory`.
- Controllers, services and repositories use **constructor injection only**. Container access is restricted to `ContainerFactory`, `CliBootstrap` and `PluginManager` — `check-architecture.php` fails the build on service-locator use elsewhere. HTTP controllers must not extend F3 `Prefab`.
- CLI tools bootstrap through `src/Application/CliBootstrap.php`, which locates `.env` via `CATTO_LEARNING_ENV_FILE`, then code root, then its parent.
- Sessions are PostgreSQL-backed (`DatabaseSessionHandler`); authentication is passwordless magic-link (`src/Auth/`).

**Persistence — two deliberate patterns, not interchangeable:**

- F3 `DB\SQL\Mapper` subclasses suffixed `M` in `src/Infrastructure/Persistence/M/` for single-table CRUD.
- `*Repository` classes using `DB\SQL` for joins, aggregates, locking and PostgreSQL-specific SQL.
- `->exec(` and mapper construction outside `src/Infrastructure/Persistence/` or a `*Repository` is an architecture-check failure. Convert rows to plain arrays inside the persistence boundary; mapper objects must never reach templates, REST or MCP responses.

Naming is enforced: `*Controller`, `*Service`, `*Repository`, `*M`.

**Never put an application object into the F3 hive.** F3 recursively escapes hive values and writes them back to public properties; `CurrentUser` is readonly, so this produces a fatal "Cannot modify readonly property". `BaseController::render()` flattens identity into scalars/arrays for exactly this reason.

There is one baseline migration: `database/migrations/20260819011500_create_v0574_baseline.php`. `check-runtime-hazards.php` asserts facts about it (e.g. `audit_log.ip_address INET` with no `ip_hash`, presence of `permissions`/`role_permissions`/`theme_registry`, absence of `theme_definitions`/`theme_files`/`theme_assets`).

## Roles, permissions, ACL

Database-driven: `roles` (uppercase `role_key`) → `role_permissions` → `permissions`, plus `user_roles`. There is deliberately **no per-user permission override table** — create another role instead.

- `ADMIN` is the immutable super-role and always holds every permission; `APP_ADMIN_EMAIL` is the recovery identity.
- Controllers guard with `requirePermission('SOME.PERMISSION')` (`BaseController`). Templates receive stable `can_*` capability booleans derived from permissions — **never hard-code role names in views or authorisation logic**.
- The 0.5.7.4 permission catalogue is knowingly too coarse for company-vs-platform resource scope. `docs/HANDOFF.md` §7 defines the required redesign; do not paper over it with role-name checks.

## Views and themes (Theme Package 3.0 / Template API 1.0 / Theme SDK 3.1)

The split is the single most important thing to get right:

- **Core owns** routes, ACL, forms, business controls, page bodies (`resources/views/pages/*.html`, `resources/views/partials/`), functional CSS (`public_html/css/catto-platform.css`), interaction JS (`public_html/js/platform-overrides.js`), and the permission-filtered `navigation` / `footer_navigation` arrays built in `ThemeRenderer`.
- **Themes own presentation only**: `base.html`, optional page-family wrappers, CSS, icon artwork. Theme JavaScript is presentation-only and themes never enforce authorisation or maintain their own route lists.
- Render pipeline (`src/View/ThemeRenderer::render()`): platform page body → optional theme page-family wrapper (`admin`/`account`/`company`/…) → active theme `base.html`. Template lookup for a child theme is child → direct parent only; child-of-child is unsupported.
- Themes are **filesystem-authoritative and immutable**; `theme_registry` is a rebuildable index, not the source of truth. Installed themes live under the instance `themes/` directory as `<slug>-v<version>`; assets are copied (never symlinked) to `public_html/themes/<key>`. Every standalone theme must define its own `base.html` and a child must ship a non-empty `public/css/theme.css`.
- Consolidated workspaces `/admin`, `/account`, `/company` are driven by `AdministrationSectionRegistry`, `AccountSectionRegistry`, `CompanySectionRegistry`; each section also has a semantic standalone route. **Do not reintroduce `/admin?tab=...`.**
- Equivalent UI patterns must reuse the same core markup/classes and the accepted theme treatment (e.g. the Administration accordion contract) across Account, Company and Help. Do not invent page-specific variants or restyle accepted designs for variety.
- `tools/validate-ui-contracts.php` and `tools/check-runtime-hazards.php` assert literal tokens in `themes/factory-reset/`, the core CSS/JS and the workspace templates — a token rename breaks the gate, so update the validator deliberately, not incidentally.
- **Known workarea gap (verified 2026/08/19):** both validators resolve the bundled theme at `themes/factory-reset/`, and so does `ThemeManager::bundledFactoryResetRoot()`. That directory does not exist here; this tree carries `factory-reset-v1.0.1`, `factory-reset-v1.0.1a` and `factory-reset-sidebar-v1.0.0`. Consequently `composer runtime:check` reports 5 errors (all from the missing `base.html`) and `validate-ui-contracts.php` fatals at line 24 (`json_decode` of the absent `theme.json` returns null). Every other runtime-hazard assertion passes. Resolve the bundled-theme path question with the owner before treating either failure as a code defect.
- External theme authors get `docs/THEME-SDK.md` alone — it is self-contained by design and must stay that way.

Gilded Noir v1.1.3 is the theme the owner actually uses; the other bundled themes are considered disposable. The accepted visual baseline is the 1.1.1/1.1.2 direction (`docs/HANDOFF.md` §9), not the broken later composition.

## Configuration

`RuntimeSettings` (`src/Configuration/`) resolves administrator-overridable settings as **PostgreSQL `options` row → `.env` → built-in default** (platform name, mail sender/DSN; SMTP secrets encrypted with `APP_KEY` via `SecretCipher`). Infrastructure values — `APP_KEY`, DB credentials, URLs, auth/session TTLs, `GEOIP_DATABASE` — stay `.env`-only. Copy `.env.example` to the instance root (alongside `public_html/`).

Anything user-visible that names the platform must read `RuntimeSettings::platformName()` / the `app_name` template variable, never `Env::string('APP_NAME')` directly.

GeoIP (Geocoder PHP + GeoLite2 City MMDB) is optional: the LMS must keep working when the file is absent, and private/local IPs are labelled as local rather than treated as errors.

## Course and commerce invariants

- Company credits are specific to course **plus access period**; approval consumes an exact matching available credit before any purchase.
- A credit is not permanently consumed until the learner explicitly starts the course; before commencement it can be unassigned/returned.
- Published courses are editable in place, and edits affect learners already in progress — this is deliberate policy, do not "fix" it back.
- Publication states: `draft`, `published`, `retired`, `archived`.
- The server owns progress, grading, unlocking, assessment marks and certificate eligibility. Imported course JavaScript / `localStorage` is never authoritative.
- Course HTML import rules are in `docs/COURSE-SPECIFICATION.md`; `LegacyHtmlCourseImporter` and `StructuredCourseImporter` are the two supported paths, with the import preview as the final conformance check.
- Web, REST and MCP entry points must call the same application services — never duplicate business logic per interface. REST lives in `src/Http/Controller/Api/` (`BaseApiController` + status/profile/course/learning controllers) with token auth, scopes and authorization in `src/Api/`; the MCP surface is `src/Mcp/LmsMcpTools.php`, whose tools (`listCourses`, `getCourse`, `listMyLibrary`, `startCourse`, `createCourse`, `setCourseStatus`) mirror the same services. Adding a capability to one surface usually means the service already exists — extend it, don't re-implement.
- `PluginManager` boots the classes listed in `config/plugins.php`, which currently returns `[]`. The hook exists for payment gateways and later integrations; plugins must not touch core files or the database directly.

- **Narrow blast radius.** Fix the requested problem only; do not redesign adjacent systems, restyle accepted visuals, or opportunistically refactor.
- **Do not release, rebuild or repackage** unless explicitly asked in that turn; if asked, build from the latest approved source, never a stale ZIP.
- Destructive dev-database reset/reseed is acceptable while the database is disposable TEST/DEV — not once the owner declares production.
- New/changed classes need class-level PHPDoc stating responsibility and architectural boundary; comments explain intent, not syntax. Add regression tests for confirmed defects and architectural contracts.
- This is pre-production: delete obsolete implementations once a canonical replacement exists rather than adding compatibility shims.
- Package validation is necessary but **browser rendering is the visual acceptance authority** — a passing validator is not proof a UI change works. Work in stages: implement, run the tests, let the owner check the UI, then move to the next stage.
