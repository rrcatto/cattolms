# Changelog

What each release of the 1.1 line brought, newest first, and what installing or updating to it needs. Releases are tagged in the repository and published on GitHub with a source zip and their notes. The releases before v1.1.0, v0.8.6 to v1.0.9, are in this file's Git history and on their GitHub release pages.

Keep this file under 150,000 characters: when it nears that, move the oldest releases out, each whole. A release's notes are not rewritten afterwards, except to add an install or update fact they left out.

## 2026-11-09 — v1.1.3 Technical SEO, the site's own logo and picture, account emails in a template, and Settings in your own order

### Installing and updating

- **No clean installation is needed:** the update runs three new upgrade migrations after the baseline (`phinx migrate`): `20261107050800_upgrade_v1_0_9_to_v1_1_0` (does nothing on v1.1.0 or later), `20261109100000_account_email_template` (which template account and order emails are drawn in) and `20261109140000_search_overrides` (a course's and a category's own words for search engines). No `.env` setting is new or removed, no package is added or removed, and no page or command is removed; `public_html/img/hero-learning.svg` and `img/hero-learning-1200x630.png` are deleted. After updating, upload the site picture at Settings > Site Owner, or the home page and the other pages without a picture of their own are shared without one. The Podman kit's update rewrites the pod's web server configuration, which now compresses text and caches the static folders. Saharan Sunset's `base.html.twig` changed (the site logo in the top bar), so the release carries Saharan Sunset 1.0.8. A site updated by the kit has rsvg-convert for SVG logos; one installed another way needs `librsvg2-bin` for them.

Course files and packages carry the names, so a course replaced from its own file keeps every part's address.

- **The API and MCP:** `/api/v1/admin/courses/{code}` and its status, and the MCP tool `set_course_status`, which takes a course code (`courseCode`) in place of a number.
- **Everything else behind a sign-in keeps its number,** such as roles, page layouts, certificate designs, reviews, enrolments, credits, refunds, ledger lines, the activity log and everything in Mailing. No guessable number opens private information to the public, and another learner's certificate number is not found.
- **Codes and keys hold a letter,** so none looks like a number in an address: a course code, a bundle code, a Course Item key, a category's and a tag's slug and a promotion code. A category's slug may not be `new`, `inline` or `field`, words its Administration addresses use, and two Course Item names with one slug are refused.
- **Emails link the new addresses:** the buyer's confirmed, how to pay, payment received and cancelled emails link `/account/orders/CL-00001042`, the approval notice the person's page and the contact notice the message's.
- **The Site Log keeps the name a path holds** (an account reference, an order or document number, a Course Item's slug, a part's name) and still hides keys, tokens and a private certificate's address.

### Signing in by Telegram, and two-step sign-in

- **Sign in with a Telegram account:** once Settings > Messages to you has Login via Telegram ticked and a bot key saved, the Sign in page offers Email address or Telegram account as feature cards, and is otherwise as before. A person connects their Telegram account at Account > Sign-in and security: Connect Telegram gives a button to the bot, the page notices Start by itself (or by I have pressed Start, without JavaScript), and Send a test and Disconnect follow. One Telegram account belongs to one person.
- **The message** holds a 6-digit code and a link, lasts 10 minutes, works once and replaces any earlier one, with its link preview off. The code works only in the browser that asked for it, and five wrong ones end it. The field takes the account's Telegram username or one of its email addresses, and the answer is the same page in the same time whether or not anything was sent. Every check an email link passes applies, and the activity log records how each sign-in was made.
- **Two-step sign-in** (RFC 6238, for any authenticator app): set up at Account > Sign-in and security with a QR code drawn on the server, or the key to type, and eight recovery codes shown once. After any sign-in link or code, and after registering, there is no session until the second step is passed, and five wrong codes end the attempt. Turning it off and new recovery codes ask for a current code, and it cannot be turned off while the site requires it of the person.
- **Who must use it:** `AUTH_TWO_STEP` (above), overridden at Settings > Two-step sign-in, straight after Who can sign in, with a Reset. Someone who must sets it up at their next sign-in, before they get in. A person's page in Administration has a Sign-in card with their Telegram account and their two-step, and Reset two-step, never on one's own page.
- **A bot serves one site for sign-in,** because the site reads the bot's messages itself, with no webhook: give each site that signs people in by Telegram its own bot. A site's messages to its owner may still share one.
- **A refused sign-in link says why:** a member of a suspended company, or someone Who can sign in keeps out, was told "The registration link is invalid or has expired." Each is now given its own reason.

### Messages to you

- **Four ticks in one row:** Login via Telegram, New Account, New Order and Payment made (the two ticks before were When someone registers and When an order is paid).
- **New Order:** a message when an order is placed at either checkout, before it is paid, once for each order (`New order: Order CL-00001042, Garden Design Basics, R1,250, to be paid by EFT (example.com)`). It is on to start with, and kept on Disconnect.

### Money Reports

- **Administration > Credits & Orders > Money Reports,** after Money Ledger and with its permission: a month's money on one page. The Month (this month so far, then every month back to the site's first records) changes the page in place, the address following, and Show does it without JavaScript.

Then Money in by method (wallet credit spent beside it, because it is not money in), Orders (placed, paid in full, still to be paid, cancelled at their deadline, refunded), Sales by course and bundle, and Refunds and payouts.

A month with no sales still goes, saying so. A month is claimed on the 1st only, and an email that cannot go is tried each minute within the sending hours for 7 days.
- **The lists the figures open count the same:** the Money Ledger's What happened offers "Card fees, to pay and to refund", Orders & Payments' Status offers "Paid in full, refunded or not", "Still to be paid" and "Refunded, in full or in part", and People shows the accounts made between two days. The dashboard's Payment fees, Awaiting payment and Refunded figures open those, so each lists what it counts.

None on Administration, account, company, sign-in, reader, preview or error pages.
- **Share pictures:** every course, bundle and landing page has the full Open Graph set and X's large picture card, with its cover as a 1200 by 630 PNG, drawn when a cover is saved, a course is made or imported or a bundle is saved. The home page has the site's own picture.
- **`/llms.txt` on a live site:** a summary of the site for AI assistants (llmstxt.org) with every published course and bundle, the help pages and the legal pages, named in robots.txt. A demo site answers not found.
- **Settings > Search engines and AI** chooses what AI crawlers may do: Allow all (the default), Allow AI search and answer assistants but block training-only crawlers, or Block all, with robots.txt naming 28 AI crawlers, each in its own group. It also holds the Google Search Console and Bing Webmaster Tools codes, bare or as the pasted meta tag, which the home page carries, how many share pictures there are, with Make the missing share pictures, and the site's addresses for crawlers.

- **A sale that starts later shows when:** a published bundle whose sale has not started stays on the Bundles page, in the catalogue and beside its courses, saying "On sale from Monday 16 November 2026 at 08:00" on its page and "On sale from 16 Nov 2026" on its card. ### Importing and exporting courses

- **The import file wins:** for a course already on the site, a catalogue package's category (made where missing), tags, prices, cover, position, layout, related courses and status replace the site's, and its content is replaced unless a learner has started it. A bundle takes the package's words, courses, price and status. The review lists every difference in plain words with Use the file's (the default) or Keep this site's, changes nothing itself, works without JavaScript and refuses an import whose review is out of date. Without the pricing or publishing permission the site's price or status stays. Two courses stay related if either file names the other, and relations to courses outside the package stay.
- **Supporting files are matched by the name the course links:** replaced in place when they differ, so every course using one gets the new file, and added when missing.
- **The single-course import** (Administration > Courses > Import, a course file or a course package) follows the same rules: matched by its code alone, each difference with Use the file's or Keep this site's, nothing replaced kept. A file with no code whose content is already a course here is refused, naming the code to give it. Where a course file is silent (prices, related courses, status, category, tags, position, layout, address, access period, certificate and style) the site's value stays. A replace keeps every part's name, a published course published and the parts open before buying, and the course takes the frame of the file just imported.
- **Downloads are named by code:** Download as one HTML file gives `YYYYMMDD-HHMM-CODE-title.html`, as `20261107-0930-GDN-101-garden-design-basics.html`, and Download with its files the same name ending `-with-its-files.zip`.
- **Course specification 4.10** says what to call the file (section 3), and **4.11** adds the names of a course's parts, `<meta name="cattolms:part-names">` (section 6.6), which CattoLMS writes so that a course replaced from its own file keeps every part's address. A course written by hand leaves it out.
- **A review or module marked not to count no longer counts:** an assessment a course file marks `data-assessment-required="false"` came in graded, so it counted towards the grade. It now comes in as practice, and a course file written from the site says `false` again.

### Identity verification

- **A live site never takes a result from Didit's sandbox,** from the webhook or on the learner's return, and records each one ignored in the activity log. A demo site takes both, so it can be tested on the sandbox.
- **The key says which it is:** a key starting `sk_test_` is the sandbox's and one starting `sk_live_` is live. A live site with a sandbox key starts no check, so certificates wait. Settings > Identity verification says which key the site has, with a danger notice for a sandbox key on a live site and a warning for a live key, whose checks are billed, on a demo site.
- **A rotated webhook secret keeps working:** for the 24 hours after a secret is rotated, Didit also signs with the old one, and those signatures are accepted.
