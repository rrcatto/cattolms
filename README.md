# Catto Learning LMS

Catto Learning is a Symfony 8.1, Twig and PostgreSQL learning-management and course-commerce platform. The current development release is **v1.2.0**, the first built on [CattoPHP](https://github.com/rrcatto/cattophp), the shared Symfony foundation that now holds its settings, activity log, roles, sign-in, page frame, components, themes, scheduler, site protection, Telegram, search engine pages, document engine, API tokens, sign-up and identity checks, Inbox and mailing. A site is installed with `deploy/podman/` or `install/install.sh` and updated in place by the same kit, which runs any database migration a release adds.

Source archives of each released version are on the GitHub [Releases](https://github.com/rrcatto/cattolms/releases) page, starting with v0.8.8.4.

Keep this README to the current release and under 150,000 characters: when something here stops being true, change it or take it out. The Git history keeps every earlier version.

## What is in the current release

- **Installation.** Two ways. `deploy/podman/` runs the site as its own user in a rootless Podman pod (web server, PHP 8.5.12 and the scheduler, the code read-only) behind the server's own web server, database and mail: see [deploy/podman/README.md](deploy/podman/README.md). `install/install.sh` installs CattoLMS on a Linux server with the server's own PHP, run as root: it asks demo or live, copies the release from GitHub to `/usr/local/lib/php/cattolms/<version>`, walks through every setting of `.env.example` into the site's `.env`, prepares the database (a clean installation), builds it, installs the themes, copies the web files to the site's `public_html` and runs the scheduler from cron. Administration → System → Setup then takes the administrator through the rest, step by step: business details, mail, payments, fees, identity verification, the theme, the starter categories and tags (`resources/catalogue/catalogue.json`) or a catalogue package from another site, importing courses, their categories, tags and covers, prices and publishing, the designs, the legal pages and going live. See [install/README.md](install/README.md).
- **Presentations.** Each module opens with a presentation played by CatWalk, and every word on every slide is measured for contrast and size by `tests/Browser/presentation-readable.cjs`. A course may have a trailer on its course page, and the site may have a presentation that introduces it at `/presentation`, linked from the front page, made in Administration like any other.
- **Catalogue packages and course codes.** Administration → Courses → Import & Export Catalogue moves courses between sites in one file, without any console command. Export: tick the courses (or Tick every course, or Tick the published courses) and download a catalogue package, a zip holding those courses as they stand on the site (their lessons and assessments, course code, cover, category, tags, position, prices and whether they are published), only their categories and tags with their icons, related course links among them and the Resource Library files they use; or download only their categories and tags. Import: upload a package and review what it would do, course by course and bundle by bundle (new, updated, unchanged or left out, with the reason), before anything changes. The file wins: a course already on the site takes the package's category, tags, prices, cover, position, layout, related courses and status, and its content unless a learner has started it, and the review lists every difference in plain words with Use the file's (the default) or Keep this site's. Supporting files are matched by the name the course links and replaced when they differ. An import whose review is out of date is refused, and the same package again changes nothing. A package also carries the bundles whose courses are all in it. Every course has a course code, such as GDN-101: capital letters and digits holding a letter, unique on the site, the same on every site, set in a course HTML file's head (`<meta name="cattolms:course-code" content="GDN-101">`), on the import review or on the Details tab, and searched in Administration → Courses. Every import matches a course by its code alone, never by its title or address, and a bundle by its own code, such as BDL-GARDEN.
- **Help, FAQ and contact.** `/help` and `/faq` open with drawn pictures and list their topics and questions as closed accordions with icons. `/contact` asks what a message is about with feature cards (Before you buy, Account Profile issue, Accounting issue, Course issue, Other) and shows that reason's own fields; every message is kept in the Inbox, emailed to the site and acknowledged to its sender with a reference.
- **The Inbox.** The top menu's Inbox holds every contact form message as a conversation with its reference (Inbox, Sent, Drafts, Spam, Trash and Settings), with the reason, course and order it names. Replies are written in plain text or HTML, each format with its own signature, with files and the person's own invoices, receipts and credit notes attached, saved as drafts or sent through the site's mail so that answers thread back. A spam check on arrival (fixed signs such as blocked countries, a form filled too fast or a throwaway address, and a word filter that learns from Mark as spam and Not spam) sets spam aside without telling the sender; blocked senders, Restore, Delete forever and Empty Trash, with Trash and Spam emptied after their settings. With a mailbox set in Inbox settings (IMAP), answers sent by email are read from it every minute and filed into their conversations.
- **The course structure and CatWalk presentations.** A module is a numbered section ("Module 1: title", from 0 when the first module sets the course up) holding its parts in order: a Presentation, a Video, the Lesson, its Summary, Flash cards, Practical work with a model answer, and the Assessment, each with its time to study and PDFs of the lesson, summary, flash cards and practical work. A Presentation is slides kept as data in twelve layouts, played by CatWalk (`docs/CATWALK.md`) one slide at a time on any screen, with narration recorded or uploaded per slide and a transcript; a trailer plays on a course's landing page. It is edited a part at a time: its page plays it at the top with its slides as a list or a grid, dragged into order; each slide has its own page with Preview, Save slide, Close and Change layout, every layout drawn as a sample slide. Arrange into modules turns an older course into module sections, a course written as one HTML file to the [course specification](docs/COURSE-SPECIFICATION-v4.13.md) imports with every part of every module, every Course Item has a unique name for administrators, learners are asked for a review when they finish, and course videos are checked every day. A course's page lists its modules with one paragraph on how a module is made, counts what the course holds, and plays its trailer in a page-wide window from Watch course presentation. Each course page is laid out by one of the site's named Course Page Layouts (Administration › Courses › Course Page Layouts) or a layout of its own, and Download as one HTML file gives the course file, which works on its own in a browser and imports back.
- **Site Analytics.** Who is on the site, where they are from and what they are doing, on the site's own server with no tracking script, its pages changing in place and updating by themselves: an Overview, the Site Log of every page asked for, Flagged Activity, a page for each address, Lockouts of an address, a range or a network owner, and automatic time-outs set at Site protection settings, with what is never timed out and how long records are kept. Optionally a lockout can also ban at the server's firewall.
- **Addresses by code and name.** No address holds a row number where a record has a code or a name. Public pages carry names, for search engines (`/courses/garden-design-basics`, `/courses/category/garden-design`), and each part of a course has its own name in the reader and the public preview (`/learn/garden-design-basics/module-1-presentation`), kept when it moves. Administration names a course by its code (`/admin/courses/GDN-101`), a person or company by account reference, an order and its invoices, receipts and credit notes by their numbers, a bundle or promotion by its code, a category or tag by its slug, a certificate by its number, a contact message by its reference and a Course Item by its name. An old numeric address is not found.
- **Signing in.** By a one-time email link, or, once the site has a Telegram bot and Login via Telegram is ticked, by a 6-digit code or link sent to the Telegram account a person connected at Account > Sign-in and security. Two-step sign-in adds a code from an authenticator app (RFC 6238, a QR code drawn on the server, eight recovery codes): `AUTH_TWO_STEP` says who must use it (`ADMINS` when it is not set), Settings > Two-step sign-in overrides it, and an administrator can reset a person's.
- **Money Reports.** Administration → Credits & Orders → Money Reports shows a month's money on one page (money in, refunds and payouts, card fees, what is left, orders paid and new accounts, each against the month before and a year before, then money in by method, orders, sales and refunds), as a PDF and an Excel file, and on the 1st of each month emails last month's to the administrator and sends its one line by Telegram.
- **Search engines and AI.** Every public page carries schema.org structured data built from what it shows, every course, bundle and landing page has a share picture drawn from its cover, a live site has `/llms.txt` for AI assistants, and Settings → Search engines and AI chooses what AI crawlers may do and holds the Google and Bing verification codes.
- **Mailing.** A Mailing menu of its own. People follow courses, categories and tags, say yes to News and Updates and join the lists an administrator makes, always with an account and an unsubscribe link in every email. The site records course changes as updates, held on Mailing › Digest until an administrator releases them; each person gets them as they happen or in a daily, weekly or monthly digest, as they chose on Account › My Subscriptions. Messages are written in blocks in a template (designed in a form, six sample designs, or HTML), proofed and sent now or later; every email has a web copy and Forward to a friend. Sending hours, an hourly limit, a gentle first day and a sending that pauses itself on bounces or complaints keep the sending trusted. News goes through a mail server or catto-mail, connected on Mailing › catto-mail with one approval. Subscribers, Automatic emails and Reports complete it.
- **Companies and people.** A company has its own domain and a person's company follows their primary address; a company always keeps an active Company Administrator; Delete keeps everything a person completed and lets someone busy with a course keep their account as a private one. A company's page and a person's page in Administration show everything about them, with their actions, on one page. A person without a picture and a company without a logo get one drawn on the server, and People, Companies, Course Creators, Courses, Subscribers and the catalogue can each be a table or a grid of cards.
- **Interface.** Every page is built one way (UX rule 1.7) on Bootstrap 6 (6.0.0-alpha.1), of which only the reboot, grid and utilities files load: fields and text use Core classes and there is no Bootstrap script. One theme is bundled, Saharan Sunset 1.0.9, and it is the default: a new site starts on it, it is read from the code and it cannot be uninstalled. The five other themes that were bundled until v1.1.0 (Gilded Noir, Light Default, Radiant Learning, Factory Reset and Factory Reset Sidebar) are out of the code and remain in the Git history at v1.1.0; Administration → Themes still uploads and installs a theme package. Saharan Sunset keeps its look in a dark operating system, and Core and every theme state the colours a reader needs in plain values, so a browser older than Bootstrap 6 still shows them. Every page is served laid out, one tab a level, and under a strict Content-Security-Policy (scripts by nonce, no inline styles).
- **Footer social media and sharing.** Settings → Footer social media sets the links behind the footer's seven marks (Facebook, WhatsApp, Telegram, X, LinkedIn, Instagram and YouTube). Every course and bundle page has one Share link: a phone's own share sheet, or on a computer a window with Facebook, WhatsApp, Telegram, LinkedIn, X, email and Copy link. Shared addresses are tagged, so Site Analytics counts the visitors who arrive through shares, by platform.
- **Catalogue.** Public course discovery reads top to bottom: a compact category picker (a native popover opening on the main categories, each branch opened as needed), the search field, then the courses: every course, 24 to a page, until a category is chosen, and then every course in that category and all its subcategories, with a light trail back up to All courses and the categories beneath as short feature cards, four to a row, each with its icon, name and description. Courses with a position in the catalogue (Details tab) come first, lowest first, then the rest newest first. Category and tag pages share the same course cards, search and pagination, and every destination also works as an ordinary GET request without JavaScript. The home page rotates Popular Courses from a stored popularity ranking (`php bin/console popularity:recalculate`). Courses show their rating from approved reviews. A course's page lays out its blocks (about the course, how a module works, the modules, at a glance, what you get, reviews, course access, ready to start, related courses) by the site's default layout or one of its own, arranged in the Page Builder: half or full width, shown or hidden.
- **Course landing pages.** A course may have one optional marketing page at `/landing/{slug}`, separate from its catalogue page, built in the course editor (Landing page) from nine kinds of section in a reorderable list: a hero (always first; its picture fills it, as wide as the cards, with the words over it, and every other section full or half width, two halves sharing a row), who the course is for, learning outcomes, course contents, benefits, reviews, pricing, FAQ and calls to action. Copy is plain text; the price, rating, approved reviews, outline (titles only) and provider are read live from the course, and the page shares the course page's buy box. It is public only while it and its course are published; ADMIN previews a draft with inert buttons. Each page has its own title, description, canonical address and sharing tags, and records first-party `landing_page_view` and `landing_page_cta_clicked` events with the campaign in its address.
- **Legal pages and the refund rule.** `/terms`, `/refunds` and `/privacy` are the Terms and Conditions, the Refund Policy and the Privacy Policy: public pages in the footer of every theme, each with a last-updated date (no version numbers) and the seller's details from the Site Owner. Both checkouts end with one required tick box that names and links the Terms and the Refund Policy, and a course checkout also asks the buyer to accept that courses start as soon as payment is confirmed; the server refuses an order without them, and the order records the dates of the documents accepted. Checkout does not ask for an identity number. ADMIN's refund action enforces the Refund Policy: a started course is never refunded, nor a bundle once any of its courses has started, and anything not started only within the refund window setting (7 days by default); ADMIN may override with a written reason, which is kept with the refund and shown on the order.
- **People named with their accounts.** Wherever a page names a person with an account, their name links to their profile (`data.person`); a page about a person or their account names them once under its title with their account reference and email; tables show the linked name alone. The People search finds anyone by name, middle name, any email address or account reference.
- **My Courses, Favourites and the wallet.** My Courses is one table with a feature card for each list (Current and Completed) and a search from five courses. Favourites is its own page, Account → Courses → Favourites, with the courses and bundles a person starred, and a company account has its Course Requests on a page of their own. A wallet's balance is a large figure in a bordered card.
- **Who can sign in.** A demo site's new accounts wait for an administrator's approval before they can sign in. `AUTH_SIGNIN` in `.env` is `ADMIN` (administrators and the addresses in `AUTH_SIGNIN_ALLOWED_EMAILS`; also when it is empty, anything else or missing) or `EVERYONE`; Settings → Who can sign in overrides both, says which is in force and resets to `.env`.
- **The Site Owner and the demo site.** The business hosting the site is the Site Owner (details from `.env`, changed at Administration → Settings → Site Owner), named on the legal pages, financial documents and certificates; there is no System Company. `APP_SITE_MODE=demo|live` (also in Settings): a demo site says so on every page and in every email, marks its orders as simulations, shows fake bank details labelled as fake and is kept out of search engines. How the program runs is `APP_ENV` alone: `development` (a server error shows its reason, templates are rebuilt, queries are logged) unless it says `production`; there is no `APP_DEBUG`, and an install never changes `APP_ENV`.
- **Accounts.** Passwordless registration and sign-in, profile, email addresses and social links. Each person has a reusable billing profile. Registration asks for the country you live in and a valid South African ID number (13 digits, a real date of birth, a citizen or permanent resident, its checksum), which gives the date of birth: the site is for adults, refuses anyone under 18 and allows one account per number. The number is kept encrypted and shown masked, and an account without one gives it at its next sign-in. Every registration is scored by the sign-up check (country, Tor, VPN and hosting networks, throwaway domains, a script browser, speed and more): a throwaway address is refused, a blocked country is held for approval without being told why, and Administration → People & Companies → Sign-up Attempts shows every attempt. Identity is verified once on Didit's hosted page (ID or passport and a live selfie, no images kept), only before a certificate and transcript, never before a purchase; a verified document showing someone under 18 stops the account. A live site never takes a result from Didit's sandbox, nor checks anyone with a sandbox key.
- **Courses.** Reusable Course Items placed in courses as a nested tree of sections (Course Components).
  - A course is a full course or a short course (Course Specification 4.13, section 15): a short course is one section of 60 to 120 minutes under its title alone, its one graded assessment completing it and making the whole mark, shown in minutes, with shorter presentations.
  - `/admin/course-items` groups shared items by course and lists Not currently in use; `/admin/resources` manages immutable local files.
  - Content is added through "+ Add here" in the Course Content tree, and moves are saved at once.
  - `/admin/courses/categories` arranges the three-level category tree: drag a category (with its subcategories) to reorder it, put it inside another or move it back out, or use the keyboard, the ⋯ menu or Move into; the server keeps every move within three levels.
  - A course's category is chosen in the same category picker on the create and edit forms and in the import review: Uncategorised, then the main categories, opening branches as needed, with + New creating a category in place at the level chosen.
  - Importing a course (a course HTML file or a course JSON package) matches it by its course code alone and follows the catalogue's rules: the file's values win, with Keep this site's for each difference, and where an HTML file is silent the site's value stays. A file with no code whose content is already a course on the site is refused, naming the code to give it. A replace keeps every part's name, so its addresses keep working. A course JSON package (`catto-learning-course` 2.1) carries the course's code and its category, tags, cover, position, related courses, prices and part names.
  - Save updates a shared item everywhere; Save As creates an independent one. Exact `[course-item:key]` references stay authored source and resolve when displayed.
- **Learning.** The learner reader is Core-owned, full-screen and white. Public previews need no enrolment and record no progress: a visitor marks parts complete and takes the public assessments on the learner's own pages, kept only in their own session. Relative availability begins at Start Course.
  - Learners mark each part of a course complete, and unmark it, with a green tick beside it in the course outline; progress counts every part done, assessments ticking themselves when submitted. Grading is unchanged: earlier graded assessments make up 50% and the final 50%.
  - Downloadable Files are served only to learners with access.
  - Learners with a genuine enrolment may rate and review a course; ADMIN approves reviews before they are public.
  - A certificate proves that the learner took the course, never that they passed: it is earned by completing every assessment, pass or fail, and issued, with a transcript of every mark, only to an account whose identity was verified (Didit's hosted page), in the verified name, with no grade. Each certificate and transcript is private until its learner makes it public at Account → My Certificates, where the learner can also give either one a new address (a random 32-digit code); the site never links to them. It is drawn in the course's certificate design. ADMIN makes designs at Courses → Certificate Designs in one form under a full-width live PDF preview: one of six looks (Classic, Modern, Minimal, Legal Seal, Gold Frame, Professional CPD) or an uploaded A4 landscape background such as a Canva design, a logo, the wording with fields, a signatory and small print. A signature picture of any size is cleaned, trimmed, fitted to the room above the signatory's name and centred on the line. A course picks its design by picture and sets its own accreditation or CPD line. The learner opens the certificate and its PDF from the course page; it keeps the values and design version it was issued with.
- **Individual commerce.** Guest and signed-in carts and a staged checkout, paying by the methods ticked at Administration → Settings → Payment methods (EFT now; card through Stitch once connected; the simulated card on a demo site only), named with their provider at checkout and on receipts, with wallet credit paying all or part of an order. Only a private account buys a course for itself; a company account asks its company. Every course starts as soon as its payment is confirmed, and fulfilment is idempotent. Invoices, receipts and credit notes are issued on the shared document engine from the order's immutable snapshots, the payment or the refund, and each keeps the values and design version it was issued with; its PDF is made once and is the same for the customer, ADMIN and the emailed invoice. ADMIN sets their logo, typeface, accent colour and closing notes at Commerce → Financial Documents, under a live PDF preview of made-up orders.
  - Promo codes apply at checkout, or apply themselves when ADMIN makes a promotion automatic: the cart then says "applied automatically", the course and bundle pages announce it, and one promotion applies to an order, the one that saves the most.
  - A course price or bundle price may be marked down from a higher was price, shown struck through beside it with the saving wherever the price appears; only the price is charged.
  - Each course price may go on sale and come off sale at a time of its own, to the minute, and one may take the default price's place while it is on sale. Buyers see and pay only prices on sale now; a published course with no price on sale stays published, cannot be bought and is listed under Needs your attention.
  - Paying by card sends the buyer to Stitch Express's own page (the site never sees a card); the order is paid when Stitch says so, on the buyer's return, by Stitch's signed webhook or by the commerce job's check every minute. Money back on a card order goes back to the card through Stitch when the refund is approved. Administration → Credits & Orders → Stitch shows the Stitch account and its payment links, payments, refunds and fees, each matched to its order. Review my order shows the checkout's steps, each line with its cover and access, who is billed, how they pay, and the order summary with the button that places the order; the checkout shows only the chosen method's details, and an invoice names the bank account only when the buyer chose EFT.
  - Course bundles (`/bundles`) sell several courses for one price; each bundled course gets its own entitlement source beside any access the learner already has. Each bundle has its own code, is edited in place in Administration → Bundles as courses are, and may go on sale later, saying when. Administration → Bundles is in the catalogue's order and dragged into it as courses are, each bundle's position within the band for its code's prefix (Settings → Bundle positions), with Renumber. A course's page names the bundles that hold it with their saving, and bundles can be favourites. In the catalogue, bundles are a section of their own above the courses, with their own cards or list, List and Grid and pages, each section paging on its own in place; each bundle has its own drawing across its card, at the head of its page and as its share picture.
  - A course stays open while any of its sources is valid, and a refund revokes only the refunded line's sources.
  - An access period's month is 30 days and each whole year 365: 6 months is 180 days, and 12 months is 365 days, shown as "1 year".
  - Every invoice, receipt and credit note opens with the buyer's account reference.
  - The buyer is emailed at every step: how to pay by EFT (bank account, account reference, amount, deadline, the invoice attached), a part payment (its receipt attached), an unpaid order cancelled at its deadline, the order confirmation with every receipt attached, and the courses that started with a link to each.
  - Refunds go to the wallet or back as money less the processor's fees; learners ask for one on the order page.
- **Companies.** People, course requests, enrolments, credits, Courses Created and Courses Bought, favourites, performance and billing details. Each member has a person page (`/company/people/{account reference}`) with their courses and course requests and the company's actions on them.
  - Only the Company Administrator buys credits, as immutable paid lots for exact course/access-period variants, and manages company billing.
  - A company buys bundles as bundle credits: one credit is the whole bundle for one person, never split between people, which the company accepts when it buys. Company → Course Credits gives a bundle credit to a person; when they already hold some of its courses it names them, and Give it anyway extends their access to those courses by the bundle's period. A bundle credit not yet given can be refunded.
- **Administration.** Courses (with each course's landing page), people, companies, enrolments, credits, Promotions, Bundles, Course Reviews, analytics events (`/admin/analytics/events`), the popularity report (`/admin/reports/popularity`), Certificate Designs (`/admin/certificates/designs`), Financial Documents (`/admin/commerce/documents`), themes, roles & ACL, settings (the Site Owner, the commerce settings and the site mode among them), the Seed Database and the UI component gallery.
  - Related courses: ticked on a course's Details tab, a relation belongs to both courses (stored once for the pair), and each course page shows its published related courses as cards.
  - Administration → Courses lists the courses in the catalogue's order, with each one's position: drag a course by its handle (or use the arrow keys on it, or the ⋯ menu) to move it; it takes the number halfway between its new neighbours, within the band for its code's prefix (Settings → Course positions, bands 10,000 apart), and a crowded run below it spreads to make room; Renumber numbers every course again from its band's start, 100 apart, in the present order. The list can be dragged while searched.
  - A category or tag takes the icon library's picture that fits its name when it is made; its page offers the icons that fit, a search of the library and an upload of one's own (an icon from an icon site is accepted and takes the theme's colour).
  - Credits & Orders: Orders & Payments, Record EFT Payment (starts from the bank statement's reference; money that pays no order goes on Unmatched Money until it is matched or paid back), Unmatched Money, the Money Ledger and Money Reports, each list filtered, searched and paged with a page per entry.
  - Settings → Connect to Telegram bot connects the site's Telegram bot, which sends the site's owner a Telegram message for each new account, each order placed and each order paid, with a Telegram log under Site Analytics. An order's page shows what happened in plain English and its ledger lines, payment events and commerce trail together.
  - The ADMIN dashboard opens with Needs your attention: one row for each thing waiting (an account to approve, a review to moderate, a company course request, an unanswered message, a money matter, an identity check, an unpublished course), naming who it concerns, saying what to do, with a button that opens that one thing. Then the period's money figures, each opening the list it adds up, and a warning when the scheduled commerce job has stopped.
  - Courses → Issued Certificates lists, searches and opens every certificate and revokes one, with its transcript, for a written reason.
  - One scheduler, `schedule:run`, runs every scheduled job and records each run: orders and emails (card payments waiting on Stitch among them), news emails, site protection, Telegram messages, Inbox answers and the monthly money report every minute (the report goes on the 1st), popularity and review requests hourly, and the clean-up, the sign-up check lists, the course video check and the log archive daily ([docs/OPERATIONS.md](docs/OPERATIONS.md), "Scheduled work").

Public readers can use:

- `/courses` to browse the catalogue;
- `/courses/category/{slug}` to browse a category branch;
- `/courses/tags` and `/courses/tag/{slug}` to browse tags;
- `/bundles` and `/bundles/{slug}` to browse course bundles;
- `/landing/{slug}` to read a course's published landing page;
- `/certificates/{public_id}` to verify a certificate and download its PDF, and `/transcripts/{public_id}` for its transcript;
- `/sitemap.xml` and `/robots.txt` (on a live site, the sitemap of published courses and landing pages; a demo site has none), and on a live site `/llms.txt`, the site's summary for AI assistants;
- `/help` for the learner-facing guide to finding, buying and completing courses, and `/faq` for short answers;
- `/contact` to write to the site;
- `/terms`, `/refunds` and `/privacy` for the Terms and Conditions, the Refund Policy and the Privacy Policy, each also a PDF (`/terms.pdf`, `/refunds.pdf`, `/privacy.pdf`).

A development database is disposable test data, which can be rebuilt from the migrations at any time. Test data is made through the pages, as people would make it: `tests/Browser/one-learner-scenario.cjs` builds an example site from a catalogue file with its courses.

## Release history

`CHANGELOG.md` holds the full notes of the 1.1 line; this is the outline. The releases before v1.1.0, v0.8.6 to v1.0.9, are in the Git history and on their GitHub release pages.

- **v1.1.0:** Addresses by code and name: Administration names each record by its code (a course by its course code, a person or company by account reference, an order and its documents by their numbers, a bundle or promotion by its code, a category or tag by its slug, a certificate, a contact message, a Course Item by its name), public pages keep names, each part of a course has a name in its address, and every old numeric address is not found, with no redirects. Signing in by Telegram, with a code or link, and two-step sign-in with an authenticator app (`AUTH_TWO_STEP`, administrators by default). Money Reports, on a page, as a PDF and an Excel file and on the 1st by email and Telegram. Search engines and AI: structured data, share pictures, `/llms.txt`, the AI crawler setting and verification codes. Bundles with codes, edited in place, on sale later saying when, as favourites, beside their courses and in the catalogue package. Favourites and Course Requests on their own pages. The canonical import: the file wins, with Keep this site's for each difference, and supporting files matched by name. Telegram's New Order message. A live site never takes a result from Didit's sandbox. Specifications 4.10 and 4.11, Lucide 1.70.0. The Privacy Policy says what Telegram sign-in and two-step sign-in keep. ## Trusted course authoring

Course import is an owner-authored workflow. Catalogue packages, course HTML files and JSON imports, subsequent edits and exports preserve authored SVG, markup, styles and embedded code. Course media uploads also accept SVG. Structural course/assessment validation and normal access controls remain in place. See [How CattoLMS handles courses](docs/COURSES.md). ## Canonical platform UI

Recurring interface structures are implemented once in CattoPHP's component registry (`CattoPHP\Ui\Components`, its templates at `@CattoPHP/ui/`), with the catalogue's own components under `resources/views/ui/catalogue/`. Views compose the registry with Twig's `ui()`, `ui_template()` and `ui_props()` APIs. The system covers layout, actions, forms, tables, datasets, statistics, lists, feedback, overlays, icons and catalogue components.

This prevents independently generated views from drifting in markup, spacing, accessibility, responsive behavior and progressive enhancement. Shared search, pagination, sortable headers, entity lookup, course cards and navigation remain canonical partials. Saharan Sunset keeps its own footer markup and decoration within the shared vocabulary. Every theme uses the canonical page vocabulary: one shell for both authentication states, shared navigation, and main/footer siblings inside `cl-page-frame`. Every page is built the same way: the page head (the only main heading, holding the page's actions), the identity band, then sections, each in a card that opens with its own heading, at the one width the page chooses (UX rule 1.7). The component gallery is available at `/admin/system/ui-components` for an administrator with the existing system settings permission.

Form controls use the bounded `ui_field_attrs(props)` helper for help/error ARIA relationships. Assessment editors clone server-rendered Twig question and option prototypes; JavaScript only reindexes those controls. Themes consume the same functional DOM while retaining their own visual design. Section-heading content starts at the left with actions at the right. Pagination remains one horizontal row and scrolls on narrow screens. Company-context banners use opaque theme tints; the core footer pairs its palette surface with a contrasting foreground. These rendered contracts are exercised in the [browser regression suite](tests/Browser/README.md).

## Architecture

- Symfony owns routing, dependency injection, security and HTTP responses.
- Routes are controller `#[Route]` attributes discovered from `src/Http/Controller/`, `src/Http/Symfony/` and `src/Commerce/Http/`.
- Controllers stay thin; application and domain services hold rules; repositories contain DBAL SQL behind the `Database` interface.
- Twig templates are strict and auto-escaped. Theme packages are filesystem-authoritative and use schema 4.0 / Template API 2.0.
- Symfony UX, Stimulus, htmx and AssetMapper provide progressive enhancement. There is no npm build step and no React, Vue or Svelte application.
- The one bundled theme is Saharan Sunset, the default, read from `themes/saharan-sunset` in the code root. Another theme is installed from its package at Administration → Themes.

## Local development

A development setup runs PostgreSQL, Mailpit, PHP-FPM, the scheduler and nginx, for example as one rootless Podman pod ([docs/OPERATIONS.md](docs/OPERATIONS.md), "Local development environment"), with a local site such as `https://catto.test/`. PHP 8.5.12 or later (8.5.12 fixes the remote code execution flaws CVE-2026-109618 and CVE-2026-109619; `composer.json` requires it) needs the extensions `composer.json` and its packages list (DOM, fileinfo, GD, iconv, JSON, libxml, mbstring, OpenSSL, PDO/PostgreSQL, XMLReader and ZIP); `composer install` refuses a server without them, and `composer check-platform-reqs --no-dev` lists what is missing. Run PHP commands as the application user, in the code directory:

```sh
composer qa
```

It runs the PHPUnit suite, PHPStan, architecture and runtime checks, UI ownership validation and release validation (which also checks that this README names the current version). `phpunit.xml` sets `memory_limit` to 512M, because a cold-cache run of the whole suite needs more than PHP's default 128M. The browser checks are Node scripts using Playwright, documented in `tests/Browser/README.md`. JavaScript changed in the repository should also pass `node --check`.

## Current boundaries

The development checkout does not include live payment processors (Stitch), automatic bank payouts, exports of the ledger and statements, gifts or debt workflows. Company credit purchasing, bank confirmation and refunds, billing profiles, promo codes and bundles, financial documents on the document engine, the money ledger, wallets, refund requests and recorded payouts, Record EFT Payment, unmatched money, the buyer's emails and Money Reports are included; VAT stays disabled, and the other areas remain later work. The legal pages carry generic text, with the seller's details from settings. Of what they describe, payment and refund payout through Stitch is not built yet; identity verification, the certificate without a grade, the transcript and the deletion of activity records after 5 years are built, and the site is for adults only: learners under 18 with a parent's consent are later work.

The database is development data. `composer smoke:install` resets it and should only be used when a deliberate reset is intended.
