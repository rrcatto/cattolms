# Catto Learning LMS

Catto Learning is a Symfony 8.1, Twig and PostgreSQL learning-management and course-commerce platform. The current development release is **v0.9.11**. Each release has a clean baseline schema: a site is installed fresh with `deploy/podman/` or `install/install.sh`, and no upgrade path from an earlier release's data is assumed.

Source archives of each released version are on the GitHub [Releases](https://github.com/rrcatto/cattolms/releases) page, starting with v0.8.8.4.

## What is in the current release

- **Installation.** Two ways. `deploy/podman/` runs the site as its own user in a rootless Podman pod (web server, PHP 8.5.12 and the scheduler, the code read-only) behind the server's own web server, database and mail: see [deploy/podman/README.md](deploy/podman/README.md). `install/install.sh` installs CattoLMS on a Linux server with the server's own PHP, run as root: it asks demo or live, copies the release from GitHub to `/usr/local/lib/php/cattolms/<version>`, walks through every setting of `.env.example` into the site's `.env`, prepares the database (a clean installation), builds it, installs the themes, copies the web files to the site's `public_html` and runs the scheduler from cron. Administration → System → Setup then takes the administrator through the rest, step by step: business details, mail, payments, fees, identity verification, the theme, the starter categories and tags (`resources/catalogue/catalogue.json`) or a catalogue package from another site, importing courses, their categories, tags and covers, prices and publishing, the designs, the legal pages and going live. See [install/README.md](install/README.md).
- **Catalogue packages and course codes.** Administration → Courses → Import & Export Catalogue moves courses between sites in one file, without any console command. Export: tick the courses (or Tick every course, or Tick the published courses) and download a catalogue package, a zip holding those courses as they stand on the site (their lessons and assessments, course code, cover, category, tags, position, prices and whether they are published), only their categories and tags with their icons, related course links among them and the Resource Library files they use; or download only their categories and tags. Import: upload a package and review what it would do, course by course (new, updated, unchanged or left out, with the reason), before anything changes; new courses take the package's prices and are published as they were, a course already on the site keeps its prices and has its content replaced only when that is ticked and nobody has started it, and the same package again changes nothing. Every course has a course code, such as GDN-101: capital letters and digits, unique on the site, the same on every site, set in a course HTML file's head (`<meta name="cattolms:course-code" content="GDN-101">`), on the import review or on the Details tab, and searched in Administration → Courses. Every import matches a course by its code alone, never by its title or address.
- **Help, FAQ and contact.** `/help` and `/faq` open with drawn pictures and list their topics and questions as closed accordions with icons. `/contact` asks what a message is about with feature cards (Before you buy, Account Profile issue, Accounting issue, Course issue, Other) and shows that reason's own fields; every message is kept, emailed to the site and acknowledged to its sender with a reference, and Administration → People & Companies → Contact Messages lists and answers them.

- **Interface.** Every page is built one way (UX rule 1.7) on Bootstrap 6 (6.0.0-alpha.1), of which only the reboot, grid and utilities files load: fields and text use Core classes and there is no Bootstrap script. Six themes are bundled: Saharan Sunset 1.0.5, Gilded Noir 2.0.7, Light Default 2.0.3, Radiant Learning 4.0.3, Factory Reset 2.0.3 and Factory Reset Sidebar 2.0.3. Each keeps its look in a dark operating system, and Core and every theme state the colours a reader needs in plain values, so a browser older than Bootstrap 6 still shows them.
- **Catalogue.** Public course discovery reads top to bottom: a compact category picker (a native popover opening on the main categories, each branch opened as needed), the search field, then the courses: every course, 24 to a page, until a category is chosen, and then every course in that category and all its subcategories, with a light trail back up to All courses and the categories beneath as short feature cards, four to a row, each with its icon, name and description. Courses with a position in the catalogue (Details tab) come first, lowest first, then the rest newest first. Category and tag pages share the same course cards, search and pagination, and every destination also works as an ordinary GET request without JavaScript. The home page rotates Popular Courses from a stored popularity ranking (`php bin/console popularity:recalculate`). Courses show their rating from approved reviews.
- **Course landing pages.** A course may have one optional marketing page at `/landing/{slug}`, separate from its catalogue page, built in the course editor (Landing page) from ten kinds of section in a reorderable list: a hero (always first), who the course is for, learning outcomes, course contents, benefits, instructor, reviews, pricing, FAQ and calls to action. Copy is plain text; the price, rating, approved reviews, outline (titles only) and provider are read live from the course, and the page shares the course page's buy box. It is public only while it and its course are published; ADMIN previews a draft with inert buttons. Each page has its own title, description, canonical address and sharing tags, and records first-party `landing_page_view` and `landing_page_cta_clicked` events with the campaign in its address.
- **Legal pages and the refund rule.** `/terms`, `/refunds` and `/privacy` are the Terms and Conditions, the Refund Policy and the Privacy Policy: public pages in the footer of every theme, each with a last-updated date (no version numbers) and the seller's details from the Site Owner. Both checkouts end with one required tick box that names and links the Terms and the Refund Policy, and a course checkout also asks the buyer to accept that courses start as soon as payment is confirmed; the server refuses an order without them, and the order records the dates of the documents accepted. Checkout does not ask for an identity number. ADMIN's refund action enforces the Refund Policy: a started course is never refunded, nor a bundle once any of its courses has started, and anything not started only within the refund window setting (7 days by default); ADMIN may override with a written reason, which is kept with the refund and shown on the order.
- **People named with their accounts.** Wherever a page names a person with an account, their name links to their profile (`data.person`); a page about a person or their account names them once under its title with their account reference and email; tables show the linked name alone. The People search finds anyone by name, middle name, any email address or account reference.
- **My Courses and the wallet.** My Courses is one table with a feature card for each list (Current, Completed, Favourite courses, and Course requests for a company account) and a search from five courses. A wallet's balance is a large figure in a bordered card.
- **Who can sign in.** A demo site's new accounts wait for an administrator's approval before they can sign in. `AUTH_SIGNIN` in `.env` is `ADMIN` (administrators and the addresses in `AUTH_SIGNIN_ALLOWED_EMAILS`; also when it is empty, anything else or missing) or `EVERYONE`; Settings → Who can sign in overrides both, says which is in force and resets to `.env`.
- **The Site Owner and the demo site.** The business hosting the site is the Site Owner (details from `.env`, changed at Administration → Settings → Site Owner), named on the legal pages, financial documents and certificates; there is no System Company. `APP_SITE_MODE=demo|live` (also in Settings): a demo site says so on every page and in every email, marks its orders as simulations, shows fake bank details labelled as fake and is kept out of search engines. How the program runs is `APP_ENV` alone: `development` (a server error shows its reason, templates are rebuilt, queries are logged) unless it says `production`; there is no `APP_DEBUG`, and an install never changes `APP_ENV`.
- **Accounts.** Passwordless registration and sign-in, profile, email addresses and social links. Each person has a reusable billing profile. The site is for adults: registration asks for the date of birth and refuses anyone under 18, and an account someone else made gives it at its first sign-in. Identity is verified once on Didit's hosted page (ID or passport and a live selfie, no images kept), only before a certificate and transcript, never before a purchase; a verified document showing someone under 18 stops the account.
- **Courses.** Reusable Course Items placed in courses as a nested tree of sections (Course Components).
  - `/admin/course-items` groups shared items by course and lists Not currently in use; `/admin/resources` manages immutable local files.
  - Content is added through "+ Add here" in the Course Content tree, and moves are saved at once.
  - `/admin/courses/categories` arranges the three-level category tree: drag a category (with its subcategories) to reorder it, put it inside another or move it back out, or use the keyboard, the ⋯ menu or Move into; the server keeps every move within three levels.
  - A course's category is chosen in the same category picker on the create and edit forms and in the import review: Uncategorised, then the main categories, opening branches as needed, with + New creating a category in place at the level chosen.
  - Importing a course that is already on the site offers to replace it: the review finds it by its course code (or, without one, by its Course Item keys), names it and chooses it under Replace, rather than listing its keys as collisions. A course JSON package (`catto-learning-course` 2.1) carries the course's code and its category, tags, cover, position, related courses and prices.
  - Save updates a shared item everywhere; Save As creates an independent one. Exact `[course-item:key]` references stay authored source and resolve when displayed.
- **Learning.** The learner reader is Core-owned, full-screen and white. Public previews need no enrolment and record no progress, and relative availability begins at Start Course.
  - Progress is assessment-only: earlier graded assessments make up 50% and the final 50%.
  - Downloadable Files are served only to learners with access.
  - Learners with a genuine enrolment may rate and review a course; ADMIN approves reviews before they are public.
  - A certificate proves that the learner took the course, never that they passed: it is earned by completing every assessment, pass or fail, and issued, with a transcript of every mark, only to an account whose identity was verified (Didit's hosted page), in the verified name, with no grade. Each certificate and transcript is private until its learner makes it public at Account → My Certificates, where the learner can also give either one a new address (a random 32-digit code); the site never links to them. It is drawn in the course's certificate design. ADMIN makes designs at Courses → Certificate Designs in one form under a full-width live PDF preview: one of six looks (Classic, Modern, Minimal, Legal Seal, Gold Frame, Professional CPD) or an uploaded A4 landscape background such as a Canva design, a logo, the wording with fields, a signatory and small print. A signature picture of any size is cleaned, trimmed, fitted to the room above the signatory's name and centred on the line. A course picks its design by picture and sets its own accreditation or CPD line. The learner opens the certificate and its PDF from the course page; it keeps the values and design version it was issued with.
- **Individual commerce.** Guest and signed-in carts and a staged checkout, paying by the methods ticked at Administration → Settings → Payment methods (EFT now; card through Stitch once connected; the simulated card on a demo site only), named with their provider at checkout and on receipts, with wallet credit paying all or part of an order. Only a private account buys a course for itself; a company account asks its company. Every course starts as soon as its payment is confirmed, and fulfilment is idempotent. Invoices, receipts and credit notes are issued on the shared document engine from the order's immutable snapshots, the payment or the refund, and each keeps the values and design version it was issued with; its PDF is made once and is the same for the customer, ADMIN and the emailed invoice. ADMIN sets their logo, typeface, accent colour and closing notes at Commerce → Financial Documents, under a live PDF preview of made-up orders.
  - Promo codes apply at checkout, or apply themselves when ADMIN makes a promotion automatic: the cart then says "applied automatically", the course and bundle pages announce it, and one promotion applies to an order, the one that saves the most (2026-10-20, not committed).
  - A course price or bundle price may be marked down from a higher was price, shown struck through beside it with the saving wherever the price appears; only the price is charged.
  - Course bundles (`/bundles`) sell several courses for one price; each bundled course gets its own entitlement source beside any access the learner already has.
  - A course stays open while any of its sources is valid, and a refund revokes only the refunded line's sources.
  - An access period's month is a twelfth of a year in whole days: 12 months is 365 days, shown as "1 year".
  - Every invoice, receipt and credit note opens with the buyer's account reference.
  - The buyer is emailed at every step: how to pay by EFT (bank account, account reference, amount, deadline, the invoice attached), a part payment (its receipt attached), an unpaid order cancelled at its deadline, the order confirmation with every receipt attached, and the courses that started with a link to each.
  - Refunds go to the wallet or back as money less the processor's fees; learners ask for one on the order page.
- **Companies.** People, course requests, enrolments, credits, Courses Created and Courses Bought, favourites, performance and billing details. Each member has a person page (`/company/people/{id}`) with their courses and course requests and the company's actions on them.
  - Only the Company Administrator buys credits, as immutable paid lots for exact course/access-period variants, and manages company billing.
- **Administration.** Courses (with each course's landing page), people, companies, enrolments, credits, Promotions, Bundles, Course Reviews, analytics events (`/admin/analytics/events`), the popularity report (`/admin/reports/popularity`), Certificate Designs (`/admin/certificates/designs`), Financial Documents (`/admin/commerce/documents`), themes, roles & ACL, settings (the Site Owner, the commerce settings and the site mode among them), the Seed Database and the UI component gallery.
  - Related courses: ticked on a course's Details tab, a relation belongs to both courses (stored once for the pair), and each course page shows its published related courses as cards.
  - Administration → Courses lists the courses in the catalogue's order, with each one's position: drag a course by its handle (or use the arrow keys on it, or the ⋯ menu) to move it; it takes the number halfway between its new neighbours, and the list is numbered again in hundreds when there is no room.
  - A category or tag takes the icon library's picture that fits its name when it is made; its page offers the icons that fit, a search of the library and an upload of one's own (an icon from an icon site is accepted and takes the theme's colour).
  - Credits & Orders: Orders & Payments, Record EFT Payment (starts from the bank statement's reference; money that pays no order goes on Unmatched Money until it is matched or paid back), Unmatched Money and the Money Ledger, each filtered, searched and paged with a page per entry. An order's page shows what happened in plain English and its ledger lines, payment events and commerce trail together.
  - The ADMIN dashboard opens with Needs your attention: one row for each thing waiting (an account to approve, a review to moderate, a company course request, an unanswered message, a money matter, an identity check, an unpublished course), naming who it concerns, saying what to do, with a button that opens that one thing. Then the period's money figures, each opening the list it adds up, and a warning when the scheduled commerce job has stopped.
  - Courses → Issued Certificates lists, searches and opens every certificate and revokes one, with its transcript, for a written reason.
  - One scheduler, `schedule:run`, runs the commerce job every minute, the popularity calculation hourly and the clean-ups daily (activity log entries and analytics events older than 5 years, expired sign-in links and sessions), recording each run.

Public readers can use:

- `/courses` to browse the catalogue;
- `/courses/category/{slug}` to browse a category branch;
- `/courses/tags` and `/courses/tag/{slug}` to browse tags;
- `/bundles` and `/bundles/{slug}` to browse course bundles;
- `/landing/{slug}` to read a course's published landing page;
- `/certificates/{public_id}` to verify a certificate and download its PDF, and `/transcripts/{public_id}` for its transcript;
- `/sitemap.xml` and `/robots.txt` (on a live site, the sitemap of published courses and landing pages; a demo site has none);
- `/help` for the learner-facing guide to finding, buying and completing courses, and `/faq` for short answers;
- `/contact` to write to the site;
- `/terms`, `/refunds` and `/privacy` for the Terms and Conditions, the Refund Policy and the Privacy Policy, each also a PDF (`/terms.pdf`, `/refunds.pdf`, `/privacy.pdf`).

A development database is disposable test data, rebuilt from the baseline whenever the schema changes. Test data is made through the pages, as people would make it: `tests/Browser/one-learner-scenario.cjs` builds an example site from a catalogue file with its courses.

## Trusted course authoring

Course import is an owner-authored workflow. HTML and JSON imports, subsequent edits and exports preserve authored SVG, markup, styles and embedded code. Course media uploads also accept SVG. Structural course/assessment validation and normal access controls remain in place. See the [course specification](docs/COURSE-SPECIFICATION.md). To recover graphics lost during an earlier import, reimport the original source.

## Canonical platform UI

Recurring interface structures are implemented once in the `PlatformUi` registry under `resources/views/ui/`. Views compose the registry with Twig's `ui()`, `ui_template()` and `ui_props()` APIs. The system covers layout, actions, forms, tables, datasets, statistics, lists, feedback, overlays, icons and catalogue components.

This prevents independently generated views from drifting in markup, spacing, accessibility, responsive behavior and progressive enhancement. Shared search, pagination, sortable headers, entity lookup, course cards and navigation remain canonical partials. Gilded Noir and Factory Reset Sidebar retain their own footer markup and shell treatment. In v0.8.5, all five themes use the canonical page vocabulary: one shell for both authentication states, shared navigation, and main/footer siblings inside `cl-page-frame`. Since v0.9.2 every page is built the same way: the page head (the only main heading, holding the page's actions), the identity band, then sections, each in a card that opens with its own heading, at the one width the page chooses (UX rule 1.7). The component gallery is available at `/admin/system/ui-components` for an administrator with the existing system settings permission.

Form controls use the bounded `ui_field_attrs(props)` helper for help/error ARIA relationships. Assessment editors clone server-rendered Twig question and option prototypes; JavaScript only reindexes those controls. Themes consume the same functional DOM while retaining their own visual design, including Gilded Noir. Section-heading content starts at the left with actions at the right. Pagination remains one horizontal row and scrolls on narrow screens. Company-context banners use opaque theme tints; the core footer pairs its palette surface with a contrasting foreground. These rendered contracts are exercised in the [browser regression suite](tests/Browser/README.md).

## Architecture

- Symfony owns routing, dependency injection, security and HTTP responses.
- Routes are controller `#[Route]` attributes discovered from `src/Http/Controller/`, `src/Http/Symfony/` and `src/Commerce/Http/`.
- Controllers stay thin; application and domain services hold rules; repositories contain DBAL SQL behind the `Database` interface.
- Twig templates are strict and auto-escaped. Theme packages are filesystem-authoritative and use schema 4.0 / Template API 2.0.
- Symfony UX, Stimulus, htmx and AssetMapper provide progressive enhancement. There is no npm build step and no React, Vue or Svelte application.
- Bundled themes are Factory Reset, Factory Reset Sidebar, Light Default, Radiant Learning, Gilded Noir and Saharan Sunset.

## Installing on a server

With rootless Podman, follow [deploy/podman/README.md](deploy/podman/README.md): a few steps as root, then one command as the site's user. With the server's own PHP, run `install/install.sh` as root on the server with the site's Linux account as its argument, then sign in with the administrator's email address and open Administration → System → Setup. [install/README.md](install/README.md) explains what the server needs, what the script asks and does, and the files it makes.

## Local development

A development setup runs PostgreSQL, Mailpit, PHP-FPM, the scheduler and nginx, for example as one rootless Podman pod ([docs/OPERATIONS.md](docs/OPERATIONS.md), "Local development environment"), with a local site such as `https://catto.test/`. PHP 8.5.12 or later (8.5.12 fixes the remote code execution flaws CVE-2026-109618 and CVE-2026-109619; `composer.json` requires it) needs the extensions `composer.json` lists (DOM, fileinfo, GD, JSON, mbstring, OpenSSL, PDO/PostgreSQL and ZIP); `composer install` refuses a server without them, and `composer check-platform-reqs --no-dev` lists what is missing. Run PHP commands as the application user, in the code directory:

```sh
composer qa
```

It runs the PHPUnit suite, PHPStan, architecture and runtime checks, UI ownership validation and release validation (which also checks that this README names the current version). `phpunit.xml` sets `memory_limit` to 512M, because a cold-cache run of the whole suite needs more than PHP's default 128M. The browser checks are Node scripts using Playwright, documented in `tests/Browser/README.md`. JavaScript changed in the repository should also pass `node --check`.

## Current boundaries

The development checkout does not include live payment processors (Stitch), automatic bank payouts, exports of the ledger and statements, gifts or debt workflows. Company credit purchasing, bank confirmation and refunds (v0.8.7), billing profiles, promo codes and bundles (v0.8.8.4), financial documents on the document engine (v0.8.9), the money ledger, wallets, refund requests and recorded payouts (v0.9.4), and Record EFT Payment, unmatched money and the buyer's emails (v0.9.5) are included; VAT stays disabled, and the other areas remain later work. The legal pages (v0.9.1) carry generic text, with the seller's details from settings. Of what they describe, payment and refund payout through Stitch is not built yet; identity verification, the certificate without a grade, the transcript and the deletion of activity records after 5 years are built (v0.9.6), and the site is for adults only: learners under 18 with a parent's consent are later work.

The database is development data. `composer smoke:install` resets it and should only be used when a deliberate reset is intended.
